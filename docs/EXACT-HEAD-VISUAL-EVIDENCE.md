# Exact-HEAD browser evidence

The Theme quality workflow must check out the **real pull-request HEAD SHA** in every job. GitHub's default `pull_request` checkout is a synthetic merge commit, which is not the same source tree as the PR head and cannot be used to label screenshots as exact-HEAD evidence. For public fork contributions, checkout uses the PR head repository plus its immutable SHA. `persist-credentials: false` keeps checkout tokens out of untrusted theme/test processes.

The WordPress browser job verifies `git rev-parse HEAD` against the event's head SHA before writing `test-artifacts/screenshots/HEAD_SHA.txt`. Its screenshot gate requires 18 Core Footnotes PNGs: three Appearance profiles on 390/1440, native target/return and Footer evidence, print, and Gutenberg editor. The Python verifier rejects missing, symlinked, malformed, truncated, CRC-corrupted, wrong-viewport, invalid-raster and mismatched-HEAD evidence. To keep validation safe, it also rejects linked screenshot directories, unknown critical PNG chunks, excessive pixel counts and oversized compressed rasters before decompression. Appearance equivalence is checked using normalized decoded-pixel fingerprints rather than compressed PNG bytes, so different PNG compression levels or row filters cannot disguise identical screenshots. It does not modify test thresholds or allow a skipped screenshot to pass.

Passing the automated gate **does not mean the layout is visually approved**. Download the `slateframe-browser` artifact from the exact successful run and actually inspect compact/default/spacious, desktop/mobile, Photography/Lightbox, Portfolio, Knowledge, Article, header/search/forms/footer, RTL/CJK, forced-colors and zoom. Reviewers must separately check mergeability and the required checks for the merge SHA on `main`. No production deployment is involved.

## Artifact provenance and file safety

The screenshot gate emits a deterministic `VISUAL_EVIDENCE.json` in the same uploaded screenshot directory. It records the immutable 40-character checkout HEAD, image dimensions, filename and SHA-256 of every required PNG, plus decoded-raster SHA-256 for the six Appearance comparisons. The manifest has no timestamp or machine-specific paths, and repeated verification yields identical bytes. This is an audit index, **not** a replacement for downloading and inspecting the images.

The verifier refuses oversized/non-regular PNGs before reading them, caps the HEAD marker, rejects symlinks anywhere in the uploaded screenshot tree (including unexpected files and linked ancestors), rejects non-image or nested artifact entries that could leak private files, and enforces PNG reserved-bit and palette-order constraints. It also binds decoded Appearance fingerprints to image dimensions so geometrically different screenshots are not incorrectly treated as identical. These checks do not change WordPress rendering, the theme's CSS/JS budgets, or CI acceptance thresholds.

## Offline review aid

`bin/visual-review-index.py` verifies the complete `BROWSER_SCREENSHOT_INVENTORY.json` against `HEAD_SHA.txt`, the required `VISUAL_EVIDENCE.json` subset, each screenshot's bytes, SHA-256, dimensions and PNG chunk CRCs. It rejects linked/unsafe files and produces a local, no-JavaScript HTML index without altering any PNG. See [offline visual review](OFFLINE-VISUAL-REVIEW.md). The index never substitutes for manual full-resolution review or the separate Photography Actions artifact.
