# Native WordPress menu depth and nested navigation

Slateframe uses the WordPress Core menu walker and does not replace menu storage, link targets, ordering, or keyboard behavior with a theme-specific menu component. A configured menu can contain more than two levels; limiting `wp_nav_menu()` to depth two silently omitted legitimate third-level links even though WordPress Core stores them. The primary menu therefore uses `depth => 0` (all authored levels). The unassigned page-menu fallback already preserves Core's page hierarchy.

## Presentation boundary

Desktop menus retain one bounded, scrollable first-level dropdown, not a cascading off-screen flyout. Third and deeper levels are rendered within that dropdown and receive a small logical start inset and border, making their hierarchy visible in both LTR and RTL. The compact disclosure retains its existing independently scrollable container, 44px links, Escape handling, focus behavior, and logical indentation. No new JavaScript, menu API, plugins, network calls, or custom walker are introduced.

## Current path visibility

WordPress Core adds `current-menu-ancestor` for configured menus and `current_page_ancestor` for page-list fallback hierarchies. Slateframe underlines those ancestor links as well as the current leaf, so readers can identify the active branch in deep menus. The theme does not infer or rewrite current classes, URLs or ARIA state. Both native class families are checked in the real WordPress/Chromium menu fixture. The fallback is already a `ul` inside the primary nav, so redundant standalone fallback list selectors were removed to keep the strict aggregate CSS envelope unchanged.

### Direct parent states

WordPress Core can also mark the direct parent with `current-menu-parent` or `current_page_parent` (notably a posts-page link), even when no ancestor class is present. Slateframe gives these native classes the same underline as current leaves and deeper ancestors, without inventing or changing Core's active-item semantics. The real WordPress Core Walker fixture temporarily removes ancestor classes to verify each parent class **in isolation** at seven widths and both text directions, checks an unrelated link remains undecorated, then restores the original Core classes for keyboard and forced-colors evidence. A dedicated 390px RTL parent-only screenshot makes the direct-parent state reviewable. The theme adds no script, walker or URL rewriting; navigation CSS is 3,665 bytes after factoring equivalent `min()` arithmetic (rather than nesting `calc()`), preserving all existing per-file and aggregate runtime budgets. The equivalent computed desktop/mobile bounds were preflighted in Chromium at eight widths × LTR/RTL.

## Acceptance

`tests/browser/navigation-deep-hierarchy.spec.js` creates a disposable three-level menu through WP-CLI, renders its HTML with the real WordPress Core `wp_nav_menu()` walker (without changing the global menu assignment), and checks it in the real theme header using WordPress/Chromium at 320, 375, 390, 412, 768, 1440 and 1920px, LTR/RTL, and 390px RTL forced colors. It requires the third-level link to remain visible and reachable through Tab, to have at least a 44px target, and not to cause document horizontal overflow. The fixture is deleted in `finally`, so other browser tests keep their own site state. The 390px RTL check also runs Axe WCAG 2/2.1 A/AA rules. CI requires all corresponding screenshots at the exact PR HEAD. `tests/test_navigation_deep_hierarchy_contract.py` guards the Core walker depth, logical nested presentation and evidence test contract. WordPress/PHP compatibility, WPCS, Theme Check, static asset budgets, screenshot integrity and human visual review remain mandatory.

## Asset envelope repair

The first PR HEAD failed 13 static tests because adding nested navigation styling exceeded existing aggregate runtime budgets (38,191/38,000 bytes for authored discussion, 43,212/43,000 bytes for photography discussion, and 25,152/25,000 bytes for the empty state). No thresholds were increased or tests skipped. Equivalent navigation CSS was nested into its existing desktop and mobile selectors, and unchanged prose declarations were grouped under their existing `.slateframe-prose` scope, while the original Core Calendar and File selectors were retained for exact existing presentation contracts. Together these changes save 292 source bytes, retaining the new logical hierarchy while preserving the pre-existing 25KB/38KB/43KB envelopes. The initial `empty` runtime envelope also required a further 65-byte navigation-selector consolidation; it is now calculated at 24,979/25,000 bytes. Existing exact-selector tests were updated to assert the equivalent nested scoped rules, without removing checks for scroll containment, media bounds or Core behavior. All resulting code must still pass the exact-new-HEAD Actions and screenshot review; a local byte calculation is not a release acceptance.
