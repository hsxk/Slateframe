# WordPress Core Tabs presentation parity

WordPress 7.1 ships native `core/tabs` with Core-owned ARIA tablist, roving focus, activation, panel visibility and fragment navigation. Slateframe does not register a competing tabs component or add runtime JavaScript. WordPress 6.7 remains supported: the conditional stylesheet is registered only if Core Tabs is available.

## Bounded presentation

The small `assets/css/core-tabs.css` stylesheet applies only when a native Tabs block renders, and is included in Gutenberg editor styles. It gives tab buttons a minimum 44px inline/block hit target using `--slateframe-control`, bounds the tab list/panels to the containing column, and allows long Japanese/Chinese/Arabic/unbroken labels to wrap at 400% text scaling. It does not override authored colors or text alignment, tab selection, hidden panels, Core button display, or Core's interactivity store. Forced-colors focus uses a system color. The selected native tab additionally has a 3px logical-block-end `Highlight` indicator, so selection is distinguishable even when forced colors remove background distinctions. The global focus offset remains in effect.

## Print completeness

The real WordPress 7.1 fixture currently emits `hidden=""` on inactive tab panels (Core's interactivity binding), while other Core implementations may emit `hidden="until-found"`. Both hide content in print unless print CSS explicitly restores display and content visibility. Slateframe's print-only stylesheet reveals either form on paper without removing or changing the original attribute, selecting another tab, or changing interactive screen and Gutenberg behavior. The original tab labels remain available for context. Real WordPress acceptance verifies LTR/RTL at 390px and computed 400% root text, print visibility and horizontal bounds, two exact-HEAD screenshots, and the restored screen-hidden state after print.

## Acceptance

`tests/browser/core-tabs-parity.spec.js` publishes a real WordPress Tabs fixture and checks 320/375/390/412/768/1440/1920 × LTR/RTL × 16/32/64px computed root text, tab target dimensions, horizontal reflow, Core keyboard focus/activation, panels and Axe. Four 390×900 viewport PNGs at 400% (LTR, RTL, RTL forced colors, and RTL forced-colors selected-tab indicator) must show the actual tab control in view. The selected-tab capture follows a real Core click, checks `aria-selected`, solid 3px indicator and viewport visibility, then restores the first tab for the original focus capture. CI verifies complete PNG chunks/CRC, dimensions and symlink safety. WordPress 6.7 installation/compatibility remains a separate gate. Safari/VoiceOver and Firefox manual testing remains a release task.

## Gutenberg serialization boundary

The authenticated editor regression in `tests/browser/core-tabs-editor-parity.spec.js` now checks WordPress's registered `core/tabs`, `core/tab-list`, `core/tab-panels` and `core/tab-panel` blocks at 390px and 1440px. It constructs nested native panels with Japanese, Chinese and Arabic labels, verifies a parse/serialize roundtrip and preserved labels, and confirms the existing editor post's serialized markup, block client IDs, and dirty state are unchanged. Gutenberg serializes Core block names using namespace-free HTML comment delimiters such as `<!-- wp:tabs -->` (not literal `core/tabs`), while the registry and parsed block tree use fully qualified `core/tabs`. The regression asserts both forms at their appropriate boundaries and exactly two native tab-panel delimiters. This is a separate contract from frontend keyboard, forced-colors and print checks: it does not claim that Safari/VoiceOver has been manually tested, nor does it introduce a theme-owned tabs block or script.

## Gutenberg 400% RTL visual reflow gate

The existing editor test checks Core registration and portable block serialization without editing the post. A separate authenticated browser regression now inserts a **disposable native Core Tabs block** into the real Gutenberg canvas at 390px and 1440px, with mixed CJK/Arabic and long unbroken labels. It verifies the browser-computed 64px root font and RTL direction, the native tab controls' 44px minimum target, label wrapping and bounded block width. It measures the existing Gutenberg canvas overflow **before** inserting the block and rejects any increase greater than 1px, without treating unrelated Core admin chrome overflow as a theme regression. It captures actual WordPress editor viewport screenshots at both widths, plus a 390px forced-colors/reduced-motion view; Browser smoke requires all three before uploading evidence. The inserted block is removed in `finally`; the test compares the original serialized content and top-level client IDs to ensure it leaves the fixture unchanged. This is a component-level editor check, not a claim that WordPress's entire admin interface has zero overflow at 400%. No theme runtime CSS, JavaScript, block registration or author content is changed.

## Disposable editor dirty-state boundary

The authenticated 400% RTL regression records Gutenberg's original `isEditedPostDirty()` alongside serialized block markup and client IDs. It marks both the temporary insertion and cleanup as nonpersistent editor changes and asserts that all three baseline properties are restored. This prevents a screenshot-only test from leaving an unsaved-change prompt or contaminating later editor checks. No authored post is saved.
