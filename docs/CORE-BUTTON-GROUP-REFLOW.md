# Native Core Buttons: responsive reflow

WordPress Core owns Buttons layout, alignment, order, width presets, vertical orientation, and Gutenberg serialization. Slateframe does not register a replacement block or add JavaScript. The shared publishing/editor rule lets direct Button flex items shrink within the available inline size; existing theme wrapping and native 44px-minimum links handle very long translated action labels. The rule retains `is-nowrap` and vertical orientation: an uncustomized Button in a non-wrapping row may shrink to its automatic minimum-content width rather than pushing adjacent actions outside the viewport. At enlarged root text sizes, the shared inline control padding is capped at 12px while retaining the configured 44px minimum target, so two translated actions can remain readable at 320px without horizontal page scrolling. Author-set custom Button widths are excluded from this shrink override. Core retains justification, ordering, and authored inline styles. Long unbroken labels wrap inside their links; no JavaScript or horizontal page clipping is needed.

The real disposable WordPress fixture publishes two Core groups: a deliberately non-wrapping row with a long CJK/Arabic/unbroken action, and a vertical group. The Chromium suite checks seven viewports (320/375/390/412/768/1440/1920), both text directions, bounded button and link geometry, 44px targets, 200%/400% text zoom, forced-colors focus, Axe and screenshots at 390/1440 plus 320 RTL/200% forced colors. A separate authenticated Gutenberg test checks native layout attributes and child Button serialization without modifying the existing editor post. Only exact-HEAD Actions evidence counts as release validation.

The shared base geometry remains in `style.css`; the forced-colors and narrow-row refinements live in the 400-byte-capped `assets/css/core-buttons.css` and are registered for the native `core/button` block. WordPress loads this layer only when a Button is rendered (including synced content and block widgets), and the editor receives it for parity. The browser fixture checks a real Button document loads this CSS while an unrelated 404 does not; the distributable ZIP must contain the asset. On WordPress 7.1.3, the actual Chromium trace records an inline `<style id="slateframe-core-buttons-inline-css">` with a sourceURL pointing at the block CSS, rather than a separate `<link>` request. The test accepts either Core-supported delivery mechanism while checking the inline content's forced-colors and nowrap rules and confirming that an unrelated 404 contains neither asset. This is a correction to the stale transport assertion, not a relaxation of runtime behavior. All pre-existing route budgets remain unchanged.

At narrow viewports (480px and below), an uncustomized two-action `is-nowrap` row shares its available inline space evenly rather than squeezing the short secondary action into a near-vertical 44px column. The 320–412px browser geometry checks require both actions to remain at least 100px wide and balanced, while desktop retains Core's natural widths and author-set custom widths remain excluded. New 320px LTR/RTL screenshots make this visual regression reviewable.

Forced-colors mode now uses the operating system's `ButtonFace`/`ButtonText` for all Core Button variants, including authored inline colors, with `Highlight` for the focused outline. This is intentionally limited to forced-colors accessibility; normal authored palette and inline styles remain unchanged. The real WordPress/Chromium suites require zero Axe contrast violations for the long-label and custom/outline fixtures under forced colors, rather than treating an outline-width check as sufficient.

Manual release acceptance still requires Safari/VoiceOver, Firefox keyboard order, actual long translated call-to-action copy, and native mobile browser text enlargement. Theme styling must not hide, disable, or replace Core links or authored Button color settings.

## Desktop long-label pair and author widths

Exact-HEAD Chromium review exposed a desktop regression missed by mobile-only readability assertions: in a native two-Button nowrap row, a very long primary label compressed the short action into a vertical-text column even at 1440px. The conditional Core Button stylesheet now reserves `min(8rem, 44%)` for each of two uncustomized actions, while leaving groups with author-defined custom widths untouched. Mobile still balances two uncustomized actions. The stylesheet remains below its existing 400-byte budget, with no global CSS or runtime JavaScript increase. Browser checks now require at least 120px for both actions at 768/1440/1920, verify custom-width bypass, and capture both LTR and RTL desktop/mobile screenshots. Do not approve from CSS inspection alone; inspect the new exact-SHA artifacts.

## 400% enlarged text and Core gap accounting

A real Chromium failure on `b9234ed` at 320px RTL and 400% root text measured **29px document overflow**. Replaying the exact failing WordPress HTML/CSS from the Actions trace isolated the off-screen element: the second native Button was 127px wide and started at -29px. WordPress Core's authored `1.25rem` group gap becomes 80px at 400% text; two 44%-minimum children then exceed the 288px content width. This is a real layout defect, not a stale assertion or an article-heading issue.

The two-action desktop readability guard now uses `min(8rem, 35%)` instead of `44%`, leaving enough inline room for Core's enlarged gap without changing the 400-byte scoped stylesheet cap, base CSS budgets, markup, author-set widths or JavaScript. The normal mobile equal-flex behavior remains. A local Chromium replay of the captured WordPress document checked all seven supported widths, LTR/RTL and 100/200/400% root text (42 combinations), with no document overflow; **this replay is diagnostic only, not GitHub Actions acceptance**. The real browser test now records the actual off-screen element boxes and a full-page 400% screenshot before failing, so future Core gap changes remain actionable. The new exact-SHA Actions and screenshots are still mandatory for release approval.
