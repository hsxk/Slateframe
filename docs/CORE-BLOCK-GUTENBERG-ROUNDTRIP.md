# Native Gutenberg Core block serialization acceptance

Slateframe's existing editor parity suite verifies the real WordPress canvas and presentation. The additional **read-only block-serialization** regression uses the installed WordPress Gutenberg `wp.blocks` registry, not a mocked serializer, to create and round-trip native `core/file`, `core/verse`, and `core/code` blocks containing Japanese, Chinese, Arabic and Korean text.

The test executes at 390px and 1440px using the disposable loopback WordPress editor fixture. It checks native registration, parsed block validity, exact deterministic reserialization and availability of Core's save element. It snapshots the existing editor's client IDs, serialized block markup and dirty state before and after. It never dispatches post edits, inserts blocks, or clicks Update, and does not persist post content. **Core login still performs genuine session authentication and may update WordPress session storage**, so the fixture must remain disposable. This deliberately does not claim database save/reload parity or visual insertion parity.

CI must run the authenticated spec serially with the existing editor tests. Passing local syntax or static contracts is insufficient: acceptance requires all necessary Actions to succeed at the exact PR HEAD SHA. Inspect the actual WordPress+Chromium screenshot artifacts for visual changes; the serialization assertions do not modify the editor DOM or produce a new screenshot.

The regression also rejects parsed blocks without an explicit `isValid === true` result. Deterministic reserialization alone can hide dropped attributes, so the test checks that Core File preserves its download URL, multilingual file name and download-button setting, and that Verse and Code retain their multilingual content after parsing. These checks exercise native Core attribute sources, not custom theme serialization.
