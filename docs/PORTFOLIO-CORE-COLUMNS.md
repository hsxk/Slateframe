# Core Query Loop column parity

The Portfolio pattern is a native WordPress Query Loop. Slateframe must respect the author's Core `columns-1` through `columns-6` choice instead of forcing three desktop columns. On tablet widths (641–900px) the layout caps at two columns without turning a deliberate single-column layout into two. At 640px and below it uses one column.

When Core chooses `is-layout-grid`, the Core grid layout remains authoritative; Slateframe only overrides the legacy flex template. The footer retains its own single-column rule. All controls, typography, links, dates and featured-image behavior remain unchanged.

Validation: `python3 -m unittest tests/test_portfolio_columns_contract.py`; `tests/browser/portfolio-core-columns.spec.js` runs against the real WordPress Portfolio fixture in Theme quality. Inspect exact-SHA 390/1440px screenshots and Core editor parity before merge. Earlier isolated Chromium verification exercised 360 combinations of 320–1920px, 1–6 columns, RTL/LTR, editor/front-end and Core Grid, but it does not replace WordPress Actions.

## Readable 200% and 400% text enlargement

A six-column Query Loop can avoid document overflow yet leave only a few characters per line at 400% text size. Slateframe uses a **named inline-size container** on the opt-in `slateframe-project-grid` pattern and a `35rem` container threshold. Since `rem` follows the root text size, native legacy-flex Post Templates collapse to one readable column at 400% for all seven supported widths, and at 200% where the container is narrower than 1120px. This is not a global viewport breakpoint or hidden overflow workaround. At normal text size, authored 1–6 columns and existing 640/900px caps remain unchanged. Authored Core `is-layout-grid` stays authoritative.

The tiny `portfolio-reflow.css` is loaded after `query-loop.css` only with a Query Loop and is shared with Gutenberg. Browsers without container queries retain the existing mobile/tablet fallback. A review caught a 641–680px regression with the former 40rem threshold: normal-size gutters could shrink the container below 640px even though the viewport was still in the two-column tablet band. The 35rem threshold retains authored 1–6 columns at 641, 650, 680, 720, 768 and 900px in LTR/RTL; two 680px baseline screenshots are mandatory. Browser acceptance exercises six authored choices, seven widths, LTR/RTL, CJK/Arabic long titles, keyboard target geometry, and Core Grid at 400%; Theme quality requires fourteen 400% LTR/RTL screenshots at all seven supported widths, two 680px tablet baseline screenshots, and a 390px RTL/400% forced-colors focus screenshot. The real WordPress browser test also runs axe WCAG 2.1 AA checks on the Portfolio region at 400%; screenshots and static contracts do not replace actual runtime verification. Manual Firefox/Safari and Gutenberg visual review remain necessary.

## Plugin and shortcode coexistence

The real WordPress MU-plugin fixture verifies that plugin-generated Portfolio markup is not silently exempt from the same opt-in presentation. The previous viewport-only 200% assertion expected two columns at 768px, although a `35rem` named container correctly reduces that layout to one readable column when the root text size becomes 32px. This was a **stale test contract**, not a reason to remove the reflow rule. The regression now independently checks normal-size columns at every viewport before increasing text size, derives the 200% expectation from the actual container content width, and retains separate author-controlled `is-layout-grid` two-column checks. It also verifies that the extra stylesheet is absent on unrelated plugin pages and present only with the Query Loop. The original 44px, RTL, overflow, forced-colors, axe and screenshot assertions remain active.

## Exact computed font-size acceptance in shortcode fixtures

The WordPress/Chromium Browser smoke on `8c10291e88a011e4a38d8a78e58fe7149b589ce1` found a real test-evidence defect: after the plugin fixture set `html.style.fontSize = '200%'`, its computed root size was **16px**, not the intended 32px. The previous percentage-based test therefore did not prove 200% enlargement in that environment. The regression now explicitly sets the standard 16px baseline, 32px for 200%, and 64px for 400%, and asserts the **computed** root size in the form, Portfolio, Core Grid and forced-colors paths. This strengthens rather than relaxes the 44px target, overflow, RTL, Core Grid and accessibility checks. The browser failure was not rerun on its original SHA; the fix requires new exact-HEAD Actions and screenshots. A different user default font size is still a manual compatibility concern, not an excuse to silently accept an un-enlarged CI fixture.

## Computed text scale and actual container width

The standalone Portfolio Core Query Loop browser suite now uses the same explicit high-priority 16/32/64px text-scale fixture as the plugin shortcode suite. Its assertions inspect the **computed root font size** at 200% and 400%, including Core Grid and native pagination, rather than assuming a percentage declaration was honored. Expected readable columns are calculated from the named container's **computed content width**, not the viewport width: page gutters and a capped reading column can make these differ. This closes a false-positive gap in the earlier Portfolio 200% CJK/RTL test, while keeping all authored columns, Core Grid, 44px targets, accessibility checks, and screenshot requirements. No production CSS or acceptance threshold is changed. Merge requires new exact-HEAD Actions success and real screenshots.
