# Current-post discussion ownership inside Core Query Loop

WordPress Core's Post Template changes the `postId` context for repeated posts. A `core/post-comments-form` or `core/comments` block inside that template belongs to the queried post, not automatically to the singular article containing the Query Loop. A blanket `has_block()` check on the outer article can wrongly suppress its classic discussion.

Slateframe preserves Core's rendering and queries. Its presentation-only ownership check excludes `core/post-template` descendants when deciding whether the *outer* singular needs the classic comments template, but still recognizes Core discussion in other children of `core/query`, direct content, nested Group/Columns, and published synced patterns outside the repeated-post context.

The existing fast path stays intact when no Query Loop or Post Template context boundary exists. The context-aware path parses Core blocks without rendering them or running shortcodes, and follows only published `wp_block` references, with cycle protection, an eight-reference depth limit, strict numeric IDs and no external requests.

The isolated PHP regression exercises 12 scenarios: Query Loop only, Query Loop plus own form, Query Loop sibling form, nested Group, published synced form, synced under Query Loop, Query Loop inside synced, mixed synced, draft reference, cycle, nested synced, and overflowing reference ID. Real WordPress/Chromium coverage checks direct and synced empty Query Loops, an outer native form, and a **populated** Query Loop containing a published page's native comments form. The populated case verifies that the repeated page's form and the outer article's classic discussion both remain available. Fixtures use distinct post types for the empty search and a unique published page title for the populated search, preventing self-matches against serialized block attributes. The real WordPress browser assertion targets `.wp-block-post-template` and its repeated-post comments form: Core emits the Post Template list directly, not a `.wp-block-query` wrapper. The first populated-fixture CI failure was a test selector error; its captured HTML already contained the queried page and nested Core form. Coverage includes 320/375/390/412/768/1440/1920, LTR/RTL, 390px RTL 400%, 1440px LTR, Axe, forced colors and nine exact-SHA screenshots. Existing WPCS, Theme Check, WP/PHP compatibility, asset budgets and package rules are unchanged.

WordPress Core references: [Post Template](https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-theme/core-block-post-template/) supplies the repeated post context; [Post Comments Form](https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-theme/core-block-post-comments-form/) consumes `postId`/`postType`. The Query Loop container itself does not supply a replacement `postId`.

## Multiple comment forms: accessibility and Core reply limitations

A populated Query Loop can render its queried page's Core form before the singular post's classic form. WordPress Core uses document-global IDs for both forms, so the later form's labels may point to the earlier form's controls. Slateframe now scopes the **theme-owned classic form's** canonical field IDs, labels, description references, form ID and submit ID only when a Query/Post Template context exists. The queried-post Core form and both `comment_post_ID` values remain untouched; plugins' custom field IDs are preserved. Local filters are removed immediately after rendering. Real browser coverage asserts label/description ownership using `document.getElementById`, not only Axe's region-level checks.

**Unresolved Core limitation / merge blocker:** WordPress `comment_form()` also emits a fixed `#respond` container and reply/cancel wiring. Multiple forms can still collide at `#respond`, `#reply-title`, and the cancel-reply target, so this field-scoping improvement alone does **not** prove threaded reply behavior is safe. Do not merge this PR until the exact-HEAD WordPress+Chromium checks explicitly verify reply/cancel interactions (or a Core-compatible design avoids the collision) and all required Actions, screenshots and ZIP reproducibility pass. Do not rewrite Core reply JavaScript or suppress the authored Query Loop form merely to satisfy a test.
